Have you ever spent a day brainstorming with an AI, going back and forth until the output is finally what you wanted?

Then something new comes up. One more piece of information it needs to know. So you paste it in, explain the situation again, and regenerate.

Then it happens again. And again.

The model was not the problem. The output was good. It was just good *in general*, and your work is never in general. Every company has its own specifics, and so does every problem inside it.

Most people try to close that gap with better prompts. I did too, for a long time.

What finally worked was moving the effort out of the prompt and into the environment the AI works in: the files it reads, the tools it can reach, the order it runs things in.

Mitchell Hashimoto calls that practice **harness engineering**. He says himself that the industry has not settled on a name for it. I am borrowing his term, and I will flag the one place where I stretch it.

## Prompt engineering was not wrong. It was incomplete.

There are three stages. It helps to see all three before arguing about tools.

**Prompt engineering** is how you phrase the request. Still a real skill, because a vague ask gets a vague answer.

But it has a ceiling. A perfect prompt about a situation the model knows nothing about still returns a generic answer, delivered with confidence.

**Context engineering** is managing what the model knows before you ask. The prompt is the question. The context is everything already in the room when the question arrives.

Most of the quality gap I used to blame on prompting turned out to live here.

**Harness engineering** is building the environment so the AI can *do* the work, not just answer. Which tools it can call. Which files it can read and write. What order it works in.

![Three isometric groups in a row, each more built up than the last: a lone sphere, then a sphere with upright slabs behind it, then both enclosed in a violet frame with a track running through.](/images/writing/from-prompt-to-harness-engineering/02-progression.webp "Each stage keeps the one before it and adds structure around it.")

This usually gets drawn as two camps: Claude and ChatGPT are chatbots, Claude Code and Codex are harnesses.

Useful as a first cut, but it is not the distinction Hashimoto draws. In his framing, what you open is an **agent**: an LLM that can chat *and* call external behaviour in a loop. Read files, run programs, make requests.

The **harness** is not the agent. It is everything you build around it. Calling Claude Code a harness collapses the two, and it hides the part that matters: the harness is yours to build, not something the vendor ships you.

The camps blur more every month anyway. The chat apps now have web search, code execution, and connectors into your own tools.

The difference that holds is not whether tools exist. It is these two:

1. **The loop.** A harness runs many steps before it comes back to you. Call a tool, read the result, notice it failed, fix it, call another. In a chat turn, you are the loop.
2. **The environment.** A harness works *inside* your file system. It opens your files and writes them back. A chatbot works *on top of* whatever you uploaded.

So read it as a spectrum, not a brand war. The question is not which product you open. It is how much work it can carry without you in the middle of every step.

## The three layers of context

"Give the AI more context" is useless advice on its own. Context comes in kinds, and the kinds behave differently. These are the three I work with.

| Layer | What it holds | Goes stale | Example file |
|---|---|---|---|
| Domain knowledge | How your field works | Quarterly, if ever | `bi-fmcg.md` |
| Tribal knowledge | How *your company* works | When people or process change | `team-operations.md` |
| Interpreted data | Where the business stands now | Weekly, sometimes daily | `sales-context.md` |

**Domain knowledge** is industry expertise. It is not about your company at all.

For me that means how a BI team works inside FMCG. Which metrics the business argues about. What a weekly sales review looks like. Which questions get asked before anyone trusts a number.

Write it once. Revisit it every few months.

**Tribal knowledge** is the layer below that. Specific to your company.

Org structure. Who owns what. How a process really runs, as opposed to how the SOP describes it. Communication lines. Which tools are in play. What the team is measured on.

This is what a new hire spends three months absorbing, and what nobody has written down. Mine becomes `team-operations.md`, so the agent knows who a finished deliverable goes to, and `meeting-notes.md`, which is how new knowledge enters the system at all.

**Interpreted data** is the current state. Recent performance, financials, live campaigns, trends. `sales-context.md`, `channel-performance.md`, `campaign-learning.md`.

This layer expires fastest. It is also the one that separates a generic answer from a useful one.

![Three stacked isometric slabs: a thick violet one at the bottom, a white one above it, and a thin top slab lifted away with a replacement hovering beside it.](/images/writing/from-prompt-to-harness-engineering/03-layers.webp "The base holds. The top gets swapped.")

**The three decay at different rates. That is the whole design constraint.**

Put them in one file and you get one of two failures. You update it rarely, so the agent reasons from last quarter's numbers. Or you rewrite it every week until you quietly stop.

Separate files, separate rhythms. The structure exists to match how fast each kind of knowledge rots.

![Three lanes on a shared timeline. Domain knowledge has one dot, tribal knowledge has three, interpreted data has thirteen.](/images/writing/from-prompt-to-harness-engineering/04-decay-rates.svg "Rewrite frequency by layer, one dot per rewrite.")

On one timeline the argument settles itself. No single file can be on all three rhythms at once.

## One flow, end to end

Here is a cycle I actually run. Not a coding one: the monthly content cycle for Abay Coffee & Listening Bar, a specialty coffee and vinyl bar in South Jakarta.

I picked it because creative work is where people assume context engineering cannot help. The output is supposed to be a judgement call.

The loop is not inside a single post. It runs once a month.

1. **Sales analysis.** The month that just closed, read for what moved and what did not. The output is a sales report. This is where AI does most of its work in the cycle.
2. **Brainstorm with the stakeholders.** A meeting, with people in it. No harness replaces this part, and nothing here is trying to.
3. **Goals for next month.** What comes out of that meeting.
4. **The campaign.** The goals become a campaign. That is where `campaign-<month>.md` comes from: one file per month, naming what we are driving at and which stage we are in.
5. **Content and visuals.** The campaign decides what gets made. Visuals come from Magnific, connected over MCP.

Then next month's numbers come in, and step 1 runs again on sales the last campaign helped produce.

![Five steps in a closed cycle: sales analysis, brainstorm with stakeholders, goals, campaign file, content and visuals, then back to sales analysis.](/images/writing/from-prompt-to-harness-engineering/05-abay-monthly-cycle.svg "The campaign file is the output of a loop that was already running.")

### Why this is the example I picked

Notice what makes `campaign-<month>.md` different from a file written to feed an agent.

Nobody added a step to the business to produce it. The sales analysis happened. The meeting happened. The goals happened. The file is just that decision, written down.

It is also the fastest-expiring layer from the table above, and the one that decides what "good" means this month.

A teaser post and a launch post are judged by different rules. Brand voice tells the agent how to sound. The campaign tells it what it is trying to achieve by sounding that way. Without it, every draft is a guess.

What is **not** in this cycle yet is a check step: something that tells the agent whether a draft fits the campaign before it reaches me. That judgement is still mine, every time.

Which is what the next section is about.

## A harness that does not improve is just a folder

Everything above is setup. What turns it into a practice is what you do when the agent gets something wrong.

Hashimoto puts it best. When the agent makes a mistake, do not just correct it in the chat. Build something so it cannot repeat the mistake.

That takes two forms.

**Instructions.** Recurring bad behaviour goes into the agent's instruction file: `AGENTS.md`, `CLAUDE.md`, whatever your setup reads. It ran the wrong command. It reached for an API that does not exist. It formatted the output wrong again.

That correction belongs in a file, not in a message you retype next week.

**Tools.** Some mistakes are not fixable with words. If the agent cannot tell whether its own work is correct, write the script that tells it. Take the screenshot. Run the filtered test. Check the output shape. Then note in the instruction file that the script exists.

The second one is what I had underrated. Put it in reverse and the goal of a harness is **to give the agent a way to check its own work**, instead of making you the checker on every run.

Context tells it what is true about your world. Tools let it test what it just produced. A harness with rich context and no checking still puts you in the loop on every output, which is where you started.

![An isometric cube with a violet track that leaves one face, arcs outward and re-enters the same cube, carrying a sphere back around, while a separate ramp sends one finished sphere out the front.](/images/writing/from-prompt-to-harness-engineering/06-verify-loop.webp "Work that fails the check returns to the machine. Only a pass leaves.")

The trigger to watch for: any time you correct the same thing twice, that correction belongs in the harness, not in the conversation.

For the Abay cycle, that is the check step. The campaign file already says what this month is driving at, so the rule for whether a draft fits is written down in everything but name.

## Where the context lives, and why plain files won

Once context is the thing you are engineering, the next question is where to keep it. My split:

- **Obsidian** for personal. Side projects, career path, learning notes.
- **Notion** for work. Project overviews, anything a client or a teammate will read.
- **Linear** for task-level context. Big things get chunked down to here.

None of that is required. A folder of `.md` files with a sensible structure does the same job. The tool matters far less than the discipline of keeping files current.

What I did stop using is Claude Projects and custom GPTs. Not because their retrieval is bad, but because of **update friction**.

Every time the context changed, I had to re-upload. With files on disk I edit the file, and the next run reads the new version. No upload, no re-indexing, no wondering which copy it is working from.

That sounds like a small convenience. It is not. Context you can only maintain through an upload step is context you will stop maintaining.

## MCP, for the context that is not in your folder

Files cover the context inside your own system. A lot of your real context is not there. It is in Slack threads, Gmail, Trello cards, a Notion database, a warehouse table.

That is what MCP (Model Context Protocol) is for: a standard way for an agent to talk to an external tool, so you are not writing a custom integration for each one.

The part I did not expect: **an MCP connection is access, not context.**

The agent can read your Notion now. It still does not know which board is the source of truth, what your statuses mean, or whether it may write anything.

So every MCP I set up gets a context file beside it. `notion-context.md` describes the boards, the update process, and what it must not touch.

### The question people ask first

Is it safe to give an AI access to your work email and Slack? It depends entirely on scope.

How I handle it: read-only wherever reading is enough. Nothing connected that can send externally or move money without a human step. Anything client-confidential stays out of the personal vault.

Worth deciding before you connect, not after.

## When a harness is overkill

I have made the case for this the whole way down. Here is the other side. Three real costs.

**Maintenance.** Context is now a thing you own. A file nobody updates becomes a confident lie. The agent will not warn you that a number is three months old. It will just use it.

Stale context is worse than no context. No context makes the output generic. Stale context makes it wrong while sounding specific.

**The files that stay current are the ones that record a decision you were already making.**

The campaign file works because that conversation happens every month whether an agent reads the result or not. Writing it down is the only added step.

A file invented purely to feed the agent, with no decision behind it, goes stale by week three. So before adding a file, check whether anything *outside* the harness forces you to keep it honest. If nothing does, you are signing up for maintenance you will not do.

**Setup overhead.** For a one-off task, writing the instruction files costs more than doing the task. A harness pays off on work that repeats: weekly reporting, research, recurring client documents. If you will do it twice, keep it in the prompt.

**Token cost and attention.** More context means more tokens per run. A context folder that grows without pruning starts hurting the output. Context engineering includes deciding what to delete.

The rule I use: build a harness when the work repeats *and* the context is stable enough to write down. Everything else, just prompt well.

![A two by two. Vertical axis: whether a decision outside the harness keeps the file current. Horizontal axis: how often the work repeats. Build the harness sits in the top right.](/images/writing/from-prompt-to-harness-engineering/07-when-to-build.svg "Repetition on its own is not enough.")

The bottom-right quadrant is the one to watch. Work that repeats feels like the obvious case for a harness, and it is, right until nothing outside the harness forces the context to stay current. That is where abandoned setups come from.

## Where to start

Do not design the whole system first. You will build a folder structure you never use.

Pick one task you already do every week. Then:

1. One folder.
2. Two files: `<task>.md` for how you want it done, and `<task>-output.md` for the shape you want the result in.
3. One flow file saying the order.

Run it. The gaps show up immediately, and they will not be the gaps you predicted. Fix those, then add the third file.

Better context produces better output, but only if the context is live. That is the whole argument.

The only way to know whether it holds for your work is to run one flow for two weeks.
